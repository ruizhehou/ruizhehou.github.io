百万 QPS 推理服务系统性优化：从模型到架构的全链路加速

140 万 QPS 意味着每秒处理 140 万次推理请求。这不是一个可以靠单机优化解决的问题，它要求模型、计算、特征、缓存、架构每一层都尽可能榨干性能，同时还要保证稳定性、可扩展性和合理的成本。

本文基于推荐/排序场景（这是最常见的百万 QPS 推理场景），系统性地梳理从模型设计到部署架构的全链路优化方法论。每一层优化不是孤立的，它们共同构成一个互相支撑的加速体系。

一、先把问题拆解清楚

在动手优化之前，先建立一个清晰的分析框架。百万 QPS 的推理服务，延迟预算通常是这样分配的：

总延迟预算（假设 P99 < 20ms）：
  网络传输：        ~1ms
  特征获取：        ~3ms   ← 常见瓶颈
  特征处理/拼接：   ~1ms
  模型前向推理：    ~8ms   ← 核心优化目标
  后处理/排序：     ~1ms
  其他（序列化等）：~1ms
  冗余：            ~5ms

140w QPS 在单机（假设每台 GPU 服务器处理 5w QPS）需要约 28 台 GPU 机器。优化的核心目标：

  • 降低延迟：保证 P99 在 SLA 以内，避免长尾
  • 提升吞吐：同等机器处理更多请求，减少机器数量，降低成本
  • 降低成本：GPU 单价昂贵，能用 CPU 处理的不用 GPU

一个关键原则：优先在模型层和特征层优化，收益最大；架构层优化是保障，而非替代前两层。

二、模型层优化：最高杠杆比

量化：用精度换速度

量化是推理加速的第一步，也是收益最确定的一步。核心思路是把 FP32/FP16 的权重和激活值降精度存储和计算。

Post-Training Quantization（PTQ，训练后量化）

# 以 TensorRT 为例，INT8 量化
import tensorrt as trt

builder = trt.Builder(logger)
config = builder.create_builder_config()
config.set_flag(trt.BuilderFlag.INT8)

# 需要提供 calibration dataset，让 TensorRT 统计激活值分布
config.int8_calibrator = MyCalibrator(calibration_data)

# 构建引擎，推理速度提升 2-3x
engine = builder.build_serialized_network(network, config)

Quantization-Aware Training（QAT，量化感知训练）

在训练时模拟量化误差，精度损失更小，适合精度敏感的排序模型：

import torch.ao.quantization as quant

# 在训练时插入 FakeQuantize 节点
model.qconfig = quant.get_default_qat_qconfig('fbgemm')
quant.prepare_qat(model, inplace=True)

# 正常训练几个 epoch 让模型适应量化误差
train(model, ...)

# 转换为真正量化的模型
quant.convert(model.eval(), inplace=True)

不同量化方案的权衡：

方案速度提升精度损失实施难度适用场景
FP161.5-2x极小低所有场景的起点
INT8 PTQ2-3x小（<0.1% AUC）中大多数 DNN 模型
INT8 QAT2-3x极小高精度敏感的排序模型
INT4 混合3-4x中（需验证）高Embedding 层压缩

推荐策略：DNN 部分用 INT8，Embedding 查表不做量化（查表本身就是整数索引，不需要量化），Attention 部分用 FP16。

模型压缩：让模型更小更快

知识蒸馏（Knowledge Distillation）

用大模型（Teacher）的软标签训练小模型（Student），是推理加速最有效的方式之一：

def distillation_loss(student_logits, teacher_logits, labels, T=4.0, alpha=0.5):
    # 软标签损失（Teacher 知识迁移）
    soft_loss = F.kl_div(
        F.log_softmax(student_logits / T, dim=-1),
        F.softmax(teacher_logits / T, dim=-1),
        reduction='batchmean'
    ) * (T ** 2)

    # 硬标签损失（真实标签监督）
    hard_loss = F.cross_entropy(student_logits, labels)

    return alpha * soft_loss + (1 - alpha) * hard_loss

实践经验：参数量减少 10x 的 Student 模型，AUC 损失通常在 0.2%-0.5% 以内，推理速度提升 5-8x，这是 ROI 最高的优化手段之一。

结构化剪枝（Structured Pruning）

整行/整列地删除权重，得到真实的稀疏结构（而非非结构化稀疏），可以直接加速矩阵乘法：

import torch.nn.utils.prune as prune

# 对 Linear 层按 L1 范数剪掉 30% 的神经元
prune.ln_structured(
    model.fc1,
    name='weight',
    amount=0.3,
    n=1,          # L1 norm
    dim=0         # 按行（输出神经元）剪枝
)

# 固化剪枝，删除被剪神经元，得到更小的矩阵
prune.remove(model.fc1, 'weight')

模型结构设计：从源头控制计算量

模型结构的选择直接决定推理成本，这是在训练阶段就必须考虑的事：

  • Deep & Shallow 分离：精排模型深（多层 MLP），粗排模型浅（2-3 层），召回模型向量化（双塔），按阶段分配计算预算
  • Embedding 维度压缩：用 PCA/AE 把高维 Embedding 降维，从 256 维压到 64 维，查表和计算量同步降低
  • 特征选择：用 SHAP/特征重要性分析删除对模型贡献低的特征，每减少一个特征就减少对应的查表和计算
  • MoE（Mixture of Experts）：每次请求只激活部分 Expert，参数量大但计算量小

三、计算优化：把硬件性能榨干

算子融合：消灭内存带宽瓶颈

推理的主要瓶颈往往不是计算（FLOPS），而是内存带宽（数据从 HBM 搬到计算单元的速度）。算子融合把多个小算子合并成一个大算子，减少中间结果的读写：

融合前：
  输入 → [MatMul] → HBM → [Add Bias] → HBM → [ReLU] → HBM → 输出
  （每个算子都要读写 HBM，3 次带宽开销）

融合后：
  输入 → [MatMul + Bias + ReLU（fused）] → 输出
  （一次计算完成，只有 1 次 HBM 读写）

TensorRT 会自动做很多融合，但对于自定义模型，可以用 torch.compile 或手写 CUDA kernel：

import torch

# torch.compile 自动进行算子融合和代码生成
@torch.compile(mode="reduce-overhead")  # 适合固定 batch size
def model_forward(x, weight, bias):
    return torch.relu(x @ weight + bias)

# 或者 mode="max-autotune" 追求极限性能（编译时间更长）
compiled_model = torch.compile(model, mode="max-autotune")

动态批处理：提升 GPU 利用率

GPU 的利用率是成本的核心。单请求推理时 GPU 利用率通常低于 20%，通过批处理可以提升到 80% 以上：

import asyncio
from collections import defaultdict

class DynamicBatcher:
    def __init__(self, model, max_batch_size=256, max_wait_ms=2):
        self.model = model
        self.max_batch_size = max_batch_size
        self.max_wait_ms = max_wait_ms
        self.pending = []
        self.lock = asyncio.Lock()

    async def infer(self, features):
        future = asyncio.Future()
        async with self.lock:
            self.pending.append((features, future))
            if len(self.pending) >= self.max_batch_size:
                await self._flush()
        return await future

    async def _flush(self):
        if not self.pending:
            return
        batch = self.pending[:self.max_batch_size]
        self.pending = self.pending[self.max_batch_size:]

        # 合并为一个 batch 推理
        batch_features = torch.stack([f for f, _ in batch])
        results = self.model(batch_features)

        # 分发结果
        for i, (_, future) in enumerate(batch):
            future.set_result(results[i])

关键参数调优：

  • max_batch_size：越大 GPU 利用率越高，但延迟越高。通常设为 64-256，需要实测
  • max_wait_ms：等待凑 batch 的超时时间，QPS 高时可以设小（0.5-2ms），QPS 低时设大（5-10ms）
  • 自适应 batch size：根据当前 QPS 动态调整，高峰期大 batch，低峰期小 batch

CUDA 级别优化

CUDA Stream 并行：把前处理、推理、后处理放到不同 Stream，流水线执行：

stream1 = torch.cuda.Stream()
stream2 = torch.cuda.Stream()

with torch.cuda.stream(stream1):
    # 异步 H2D 数据传输（CPU → GPU）
    gpu_features = features.to('cuda', non_blocking=True)

# 等 H2D 完成后推理
stream2.wait_stream(stream1)
with torch.cuda.stream(stream2):
    output = model(gpu_features)
    # 异步 D2H 结果传输
    result = output.to('cpu', non_blocking=True)

内存池（Memory Pool）：避免频繁的 cudaMalloc/cudaFree，用预分配内存池：

import torch.cuda

# 设置内存分配器，减少碎片
torch.cuda.set_per_process_memory_fraction(0.8)
# PyTorch 默认已经有 caching allocator，可以进一步调优
torch.cuda.memory.set_allocator_settings("expandable_segments:True")

Tensor Core 利用：确保矩阵维度是 8/16 的倍数，让 GPU 的 Tensor Core 充分工作：

Bad:  Linear(257, 100)  → 不对齐，Tensor Core 利用率低
Good: Linear(256, 128)  → 对齐，Tensor Core 满载运行

四、特征工程优化：最容易被忽视的瓶颈

在实际系统中，特征获取和处理的耗时往往超过模型推理本身。140w QPS 意味着每秒要完成 140 万次特征查询。

特征缓存体系

特征缓存架构（三级缓存）：

请求到来
  ↓
L1: 进程内缓存（Python dict / LRU Cache）
    命中率：~30%，延迟：~0.01ms，容量：数万条
  ↓（miss）
L2: 本地 Redis / Aerospike（同机房）
    命中率：~60%，延迟：~0.5ms，容量：数百万条
  ↓（miss）
L3: 分布式特征存储（Hologres / Doris / Redis Cluster）
    命中率：~100%，延迟：~3ms，容量：数十亿条

缓存策略要点：

  • 用户特征：更新频率低（分钟级），TTL 可以设 5-10 分钟，命中率高
  • 物品特征：静态特征 TTL 1 小时，动态特征（曝光数、点击率）TTL 1 分钟
  • 实时特征（近 1 小时行为）：不缓存或极短 TTL（10 秒），必须从流式存储实时查
  • 预热：服务启动时预加载热门用户/物品特征到 L1，避免冷启动时的 cache miss 风暴

特征并行获取

不同来源的特征（用户特征、物品特征、上下文特征）独立查询，并行获取，不要串行等待：

import asyncio

async def get_all_features(user_id, item_ids, context):
    # 并行查询三类特征，不串行等待
    user_feat, item_feats, ctx_feat = await asyncio.gather(
        get_user_features(user_id),
        get_item_features(item_ids),  # 批量查询
        get_context_features(context)
    )
    return merge_features(user_feat, item_feats, ctx_feat)

特征预计算与异步更新

能提前算的特征提前算好存起来，不在推理时实时计算：

  • 用户画像特征：每天跑一次离线任务，把用户的长期兴趣向量写入 KV 存储
  • 物品统计特征：每 5 分钟更新一次点击率、转化率，推理时直接查
  • 交叉特征：高频的用户-物品交叉特征预计算好，避免推理时实时笛卡尔积
  • Embedding 预计算：用户 Embedding 和物品 Embedding 提前算好，推理时只做点积

五、结果缓存与请求优化

推理结果缓存

对于相同的请求，缓存推理结果可以直接绕过推理计算：

import hashlib, json

def get_cache_key(features: dict) -> str:
    # 对特征做规范化排序后哈希，相同特征得到相同 key
    normalized = json.dumps(features, sort_keys=True)
    return hashlib.md5(normalized.encode()).hexdigest()

async def infer_with_cache(features):
    key = get_cache_key(features)

    # 先查缓存
    cached = await redis.get(key)
    if cached:
        return json.loads(cached)

    # 缓存 miss，做推理
    result = await model.infer(features)

    # 写入缓存，TTL 根据业务设置（推荐场景通常 10-30 秒）
    await redis.setex(key, 15, json.dumps(result))
    return result

注意：结果缓存适合相同用户短时间内重复请求（如频繁刷新）的场景，对于每次请求特征差异大的场景（实时特征多）命中率低，不适合。

请求合并（Request Coalescing）

对于候选集重叠度高的请求（如多个用户都在看同一批热门物品），合并推理：

请求 A：user_1 × [item_1, item_2, item_3, item_4]
请求 B：user_2 × [item_2, item_3, item_5, item_6]

合并后：物品特征只查一次 [item_1..item_6]，复用计算
（适合召回结果重叠度高的场景，如热门 feed 流）

提前退出（Early Exit）

在多级漏斗（粗排→精排）中，低分候选提前淘汰，不进入精排：

async def ranking_pipeline(user_id, candidates):
    # 粗排：快速过滤，保留 top 500
    coarse_scores = await coarse_ranker.infer(user_id, candidates)
    top500 = sorted(zip(candidates, coarse_scores), key=lambda x: -x[1])[:500]

    # 精排：只对 top 500 做精细计算
    fine_scores = await fine_ranker.infer(user_id, [c for c, _ in top500])

    # 重排：只对 top 50 做多样性优化
    top50 = sorted(zip([c for c, _ in top500], fine_scores), key=lambda x: -x[1])[:50]
    return reranker.rerank([c for c, _ in top50])

每级计算量差一个数量级：精排计算量是粗排的 1/10，重排是精排的 1/10，总计算量减少 90% 以上。

六、部署架构优化

服务分层与算力分配

推荐系统典型分层架构：

用户请求（140w QPS）
     ↓
召回层（向量检索，CPU 集群）
  · ANN（近似最近邻）：FAISS / ScaNN
  · 每次请求：100ms 级，返回 1000 个候选
  · CPU 密集，横向扩展
     ↓（1000 候选）
粗排层（轻量模型，CPU 或 GPU）
  · 2-3 层 MLP，<1ms 延迟
  · 过滤到 200 个候选
     ↓（200 候选）
精排层（深度模型，GPU 集群）  ← 主要优化目标
  · Transformer / DIN / DIEN 等
  · 5-15ms 延迟
  · 过滤到 50 个候选
     ↓（50 候选）
重排层（规则 + 轻量模型）
  · 多样性、时效性调整
  · <1ms
     ↓
最终结果（20-50 个）

异构计算：GPU 做精排，CPU 做其他

GPU 昂贵，只应该用在 GPU 必要的地方（矩阵密集计算）。召回、粗排、特征处理都应该跑在 CPU 上：

任务推荐硬件原因
向量召回（ANN）CPU（高内存）内存访问密集，GPU 无明显优势
粗排（浅层 MLP）CPU 或 GPU模型小，GPU 利用率低，CPU 可胜任
精排（深层模型）GPU（A100/H100）矩阵乘法密集，GPU 优势明显
特征处理CPU逻辑复杂，不适合 GPU
Embedding 查表CPU（大内存）内存随机访问，GPU 显存放不下

负载均衡与弹性扩缩容

推理服务的流量通常有明显的日/周规律（早晨、午间、晚间高峰）。弹性伸缩是降成本的关键：

服务稳定性保障

百万 QPS 下，任何一点不稳定都会被放大成严重的业务影响：

熔断与降级

from circuitbreaker import circuit

@circuit(failure_threshold=5, recovery_timeout=30)
async def call_ranking_model(features):
    """精排服务熔断：5 次失败后熔断，30 秒后尝试恢复"""
    return await ranking_model.infer(features)

async def get_ranking_result(features):
    try:
        return await call_ranking_model(features)
    except CircuitBreakerError:
        # 降级：用粗排结果或规则兜底，保证有结果返回
        return await fallback_coarse_ranking(features)

超时控制

async def infer_with_timeout(features, timeout_ms=10):
    try:
        return await asyncio.wait_for(
            model.infer(features),
            timeout=timeout_ms / 1000
        )
    except asyncio.TimeoutError:
        # 超时降级，返回缓存结果或默认排序
        return get_default_result()

流量控制（限流）：用令牌桶或漏桶算法限制单用户请求频率，防止异常流量打垮推理服务。

七、Embedding 优化：大规模稀疏特征的专项处理

推荐系统的 Embedding 表可以有数亿甚至数千亿个 ID（用户 ID、物品 ID、各种统计特征 ID），远超 GPU 显存容量。

分级存储策略

Embedding 存储架构：

热门 ID（Top 1%，覆盖 80% 请求）
  → 放 GPU 显存（最快，容量最小）
  → A100 80GB，可放约 2 亿个 64 维 FP16 向量

中等热度 ID（Top 10%）
  → 放 CPU 内存（较快，容量中等）
  → 1TB 内存，可放约 130 亿个向量

长尾 ID（剩余 90%，但只占 20% 请求）
  → 放 SSD 或分布式 KV（慢但容量大）
  → Aerospike / Redis，延迟 1-3ms

Embedding 压缩

  • 降维：训练时用 256 维，推理时 PCA 降到 64 维，查表速度提升 4x
  • 哈希压缩：多个低频 ID 哈希到同一个 Embedding，减少 Embedding 表大小
  • Compositional Embedding：把大 Embedding 表分解为多个小 Embedding 的组合，显存减少 10-100x
class CompositionalEmbedding(nn.Module):
    """把一个大 Embedding 表分解为多个小表的笛卡尔积"""
    def __init__(self, num_ids, embed_dim, num_tables=4):
        super().__init__()
        # 4 个小表，每个 sqrt(num_ids) 行，内存 1/4
        table_size = int(num_ids ** (1/num_tables)) + 1
        self.tables = nn.ModuleList([
            nn.Embedding(table_size, embed_dim // num_tables)
            for _ in range(num_tables)
        ])

    def forward(self, ids):
        # 把 id 分解到各个子表的索引
        sub_ids = decompose_id(ids, len(self.tables))
        # 拼接各子表的 Embedding
        return torch.cat([t(sub_ids[i]) for i, t in enumerate(self.tables)], dim=-1)

八、监控体系与持续优化

优化是持续的过程，完善的监控体系是持续优化的基础。

关键指标体系

性能指标：
  · QPS：总请求量，分服务/模型/接口粒度
  · 延迟：P50 / P90 / P99 / P999，关注长尾
  · GPU 利用率：目标 70-80%（太低浪费，太高不稳定）
  · GPU 显存利用率
  · CPU 利用率
  · 特征缓存命中率（L1/L2/L3 分别统计）

业务指标：
  · 模型 AUC / GAUC
  · 点击率、转化率（最终效果指标）
  · 降级率（熔断/超时触发的频率）

成本指标：
  · 单次推理成本（GPU 时 / 1000 次推理）
  · 机器利用率（扣除闲置时间）

九、优化路线图：按优先级推进

面对一个 140w QPS 的推理服务，从哪里下手？按投入产出比排序：

阶段一：低垂果实（1-2 周，收益大）
  ✓ FP16 推理（直接 2x 加速，几乎无精度损失）
  ✓ 动态批处理（GPU 利用率从 20% → 70%+）
  ✓ 特征缓存命中率优化（降低特征获取延迟）
  ✓ 并行特征获取（消除串行等待）

阶段二：模型优化（2-4 周，需要训练验证）
  ✓ INT8 PTQ 量化（再提 2x，需要精度验证）
  ✓ 知识蒸馏小模型（5-8x 加速，最高收益）
  ✓ 特征裁剪（删除低 SHAP 特征，减少特征查询量）

阶段三：架构优化（1-2 个月，改动较大）
  ✓ 分级漏斗（粗排过滤，减少精排计算量）
  ✓ Embedding 分级存储（解决显存瓶颈）
  ✓ 弹性扩缩容（降低闲置成本）

阶段四：深度优化（持续迭代）
  ✓ 算子融合 / CUDA 优化
  ✓ Compositional Embedding 压缩
  ✓ 在线学习 + 增量更新（保持模型新鲜度同时降低训练成本）

十、关键点总结

  • 建立延迟预算：把总延迟 SLA 分解到每个环节，量化每个环节的优化空间，先攻击最大的瓶颈
  • 量化是第一步：FP16 几乎无损，INT8 需要验证精度，先做 FP16，再评估 INT8
  • 知识蒸馏是 ROI 最高的手段：一个蒸馏出来的小模型可以获得大模型 99% 的效果，同时推理速度提升 5-8x
  • 动态批处理是 GPU 利用率的关键：单请求推理 GPU 利用率极低，批处理是必选项
  • 特征延迟常常比模型延迟更高：三级缓存体系 + 并行获取是特征层优化的核心
  • 分级漏斗是架构层最有效的手段：粗排→精排→重排，每级计算量差一个数量级
  • Embedding 专项处理：百亿级 Embedding 表放不进 GPU，分级存储 + Compositional Embedding 是解法
  • 稳定性优先于极致性能：熔断、降级、超时控制是百万 QPS 服务的必备能力，不能为了追求性能而牺牲稳定性
  • 监控驱动优化：没有完善的监控，优化是盲目的。每一次优化都需要有指标来衡量效果
