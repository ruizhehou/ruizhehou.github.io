百万 QPS LLM 推理服务系统性优化

140 万 QPS 的 LLM 完整对话推理，是当今技术栈中最极限的工程挑战之一。OpenAI、Google、字节、百度等少数公司才能运营这个量级的服务。在这个规模下，优化的每一个百分点都意味着数亿元的成本节省或能服务更多用户。

本文从 LLM 推理的本质出发，系统性地梳理每一层优化手段。LLM 推理与传统深度学习推理有根本性的不同——它的瓶颈不是算力，而是显存带宽和 KV Cache 管理，理解这一点是所有优化的起点。

一、先做规模估算：理解问题的量级

在动手优化之前，先把问题的规模感建立起来。以 Llama-70B 为例，假设平均对话输入 500 token、输出 200 token：

每秒新增请求：                 140 万
每个请求占 GPU 时间（decode）：约 3 秒
同时在飞行中的并发请求：        140万 × 3s ≈ 420 万并发

单张 A100-80GB 运行 Llama-70B（TP=8）：
  最大并发：约 80-120 个请求（受 KV Cache 显存限制）
  吞吐：约 3000-6000 token/s

需要的 8 卡节点数：
  420万并发 ÷ 100并发/节点 = 4.2 万节点
  = 33.6 万张 A100

成本：按 A100 租金 $2/小时，每小时成本 ~$67 万

这是基于 Llama-70B FP16 的悲观估算。实际大厂的做法通常会让数字好看得多：

  • 用 INT4/FP8 量化：显存减半，同等卡数并发翻倍
  • 用蒸馏的更小模型（7B/14B）：参数量少 5-10 倍，速度对应提升
  • 不是所有 140w QPS 都是长输出，很多是短问答（20-50 token），占用时间短
  • Prefix Caching 命中时 prefill 几乎免费，有效吞吐大幅提升

但无论如何，两件事是确定的：

  1. 每提升 1% 的吞吐量，在这个规模下每年节省数百万到数千万美元
  2. 这是一个显存带宽密集型问题，每个优化手段都要从"如何减少显存读写"出发

二、LLM 推理的本质：为什么它和传统推理完全不同

两阶段计算特性

LLM 推理分为两个性质完全不同的阶段：

Prefill 阶段（处理输入 prompt）：
  - 对所有输入 token 并行计算 Attention
  - 计算密集（Compute-bound），算力是瓶颈
  - 一次完成，生成初始 KV Cache
  - 延迟：与 prompt 长度成正比

Decode 阶段（逐 token 生成输出）：
  - 每步只生成 1 个新 token
  - 显存带宽密集（Memory-bound），带宽是瓶颈
  - 串行执行，无法并行化
  - 延迟：与输出长度成正比，每步约 20-100ms

这两个阶段的性质不同，决定了它们需要完全不同的优化策略，甚至需要部署在不同的硬件上。

KV Cache：显存的核心消耗

Transformer 的 Attention 机制要求保存每一层每一个已生成 token 的 Key 和 Value 向量，这就是 KV Cache：

KV Cache 大小 = 2（K+V）× 层数 × 注意力头数 × 头维度 × 序列长度 × 精度字节数

以 Llama-70B（80层，64头，128维，FP16）为例：
单个请求，序列长度 1000 token，整个集群（TP=8 时所有卡合计）：
  2 × 80 × 64 × 128 × 1000 × 2 bytes
  = 2,621,440,000 bytes ≈ 2.44 GB（8 卡合计）

每张卡只存 1/8：2.44 GB ÷ 8 ≈ 305 MB

8 卡 A100-80GB，模型权重总显存：140B × 2bytes = 280GB，每卡 35GB
每卡可用于 KV Cache：80 - 35 = 45 GB
每卡最大并发：45 GB ÷ 305 MB ≈ 147 个请求
8 卡节点整体：约 150 个并发请求（受限于卡间同步开销）

注意：这是单个节点能服务的并发上限，序列越长、显存越紧张。

这就是为什么显存管理是 LLM 推理的核心问题——不是算力不够，而是 KV Cache 把显存占满了。

三、Continuous Batching：最高优先级的优化

传统批处理（Static Batching）的问题：等所有请求都到齐再一起推理。结果是：短请求生成完了还要等长请求，GPU 大量时间在空转。

Static Batching（传统）：
  Batch = [req1(200tok), req2(50tok), req3(180tok)]

  时间轴：|==req1(200步)==|
          |=req2(50步)====等等等等等|  ← req2 完成后 GPU 空转
          |==req3(180步)==========|
  GPU 利用率：~30%

Continuous Batching（连续批处理）：
  时间轴：|req1 step1|req1 step2|...|req1 step200|
          在每一步，把已完成的请求移出，把新到的请求加入

  |req1+req2+req3 step1|...|req2完成，req4加入|...
  GPU 利用率：~80%+

实现原理：每个 decode step 结束后，检查哪些序列已完成（生成了 EOS token），把它们移出 batch，同时把等待队列中的新请求加入。这样 GPU 每一步都满载运行。

vLLM、TGI（Text Generation Inference）、SGLang 都默认实现了 Continuous Batching。这是 LLM 推理的基础设施，必须上。

四、PagedAttention：KV Cache 的革命性管理

PagedAttention 是 vLLM 的核心创新，灵感来自操作系统的虚拟内存分页。

传统 KV Cache 的问题

传统方式：为每个请求预分配连续的最大长度显存
  请求最大长度 2048 token → 预分配 2048 token 的显存

  实际情况：
  [req1: 实际用了 200 token，其余 1848 空着]  ← 内部碎片
  [req2: 实际用了 500 token，其余 1548 空着]
  [req3: 等待中，但显存已被预占]              ← 外部碎片

  显存利用率：~30%

PagedAttention 原理

PagedAttention：KV Cache 不预分配，按需分页（每页 16 token）

Block Table（逻辑页 → 物理页映射）：
  req1: [逻辑页0 → 物理块3][逻辑页1 → 物理块7][逻辑页2 → 物理块1]
  req2: [逻辑页0 → 物理块5][逻辑页1 → 物理块9]

物理显存：
  [块1: req1的token17-32][块2: 空闲][块3: req1的token1-16]
  [块4: 空闲][块5: req2的token1-16]...

  显存利用率：~90%（只有最后一个不满的块有浪费）

更重要的是，PagedAttention 天然支持 KV Cache 共享——如果两个请求有相同的前缀（比如相同的 System Prompt），它们可以共享同一批物理块，完全不占额外显存。

# vLLM 使用示例
from vllm import LLM, SamplingParams

llm = LLM(
    model="meta-llama/Llama-3-70b-instruct",
    tensor_parallel_size=8,        # 8 卡张量并行
    gpu_memory_utilization=0.90,   # 90% 显存给 KV Cache
    max_num_seqs=512,              # 最大并发序列数
    enable_prefix_caching=True,    # 开启前缀缓存（共享 System Prompt）
)

sampling_params = SamplingParams(
    temperature=0.7,
    max_tokens=512,
)

outputs = llm.generate(prompts, sampling_params)

五、Prefix Caching：System Prompt 只算一次

生产环境的 LLM 服务几乎所有请求都有相同的 System Prompt（"你是一个有帮助的助手..."），长度通常 200-1000 token。每个请求都重复计算这部分是巨大的浪费。

没有 Prefix Cache：
  每个请求 = Prefill(system_prompt + user_input) + Decode
  1000 token system prompt × 140w QPS = 每秒 14 亿 token prefill 计算

有 Prefix Cache：
  第一个请求：计算并缓存 system_prompt 的 KV Cache
  后续请求：直接加载缓存，只 prefill user_input 部分
  节省：~60-80% 的 prefill 计算量

Prefix Caching 的实现依赖 PagedAttention 的分页结构——相同前缀的逻辑页映射到同一批物理块，物理块引用计数管理生命周期。

SGLang 的 RadixAttention 把这个概念进一步扩展——用 Radix Tree 管理所有历史请求的 KV Cache，不仅 System Prompt，连多轮对话的历史也可以复用，命中率更高。

六、投机解码（Speculative Decoding）：吞吐提升 2-3 倍

Decode 阶段每步只生成 1 个 token，GPU 大量时间在等待显存读取（memory-bound）。投机解码的思路是：用小模型同时猜测多个 token，用大模型一次性验证。

标准 Decode：
  大模型每步处理 1 个 token → 生成 1 个 token
  100 个 token = 100 步

投机解码（Draft + Verify）：
  Step 1: 小模型（Draft Model）预测接下来 5 个 token：[the, cat, sat, on, the]
  Step 2: 大模型一次性验证这 5 个 token（计算量 ≈ 5 步，但实际只用 1 步时间）
          - 验证结果：[the ✓][cat ✓][sat ✓][on ✗]
  Step 3: 接受前 3 个 token，从"on"开始重新生成
  净收益：1 步验证 = 生成 3+ 个 token（接受率越高收益越大）

接受率取决于 Draft Model 和 Target Model 的分布差异。通常：

  • 同系列小模型（如 Llama-7B draft + Llama-70B target）：接受率 70-85%，吞吐提升 2-3x
  • n-gram 匹配（不用额外模型，直接用历史文本预测）：接受率 40-60%，吞吐提升 1.5-2x，适合代码生成等重复性强的场景

关于延迟的准确表述：投机解码提升的是吞吐量，对单请求延迟的影响取决于接受率。接受率高时（>70%），同样长度的输出所需步骤更少，端到端延迟可以降低；但如果接受率低，Draft Model 的推理开销会反而增加延迟。因此说"不牺牲延迟"不够严谨——在典型接受率（70%+）下延迟持平或略降，但接受率低时需谨慎。生产上建议先测量具体业务的 Draft 接受率再决定是否启用。

# vLLM 中使用投机解码
llm = LLM(
    model="meta-llama/Llama-3-70b-instruct",
    speculative_model="meta-llama/Llama-3-8b-instruct",  # Draft model
    num_speculative_tokens=5,   # 每次猜 5 个 token
    tensor_parallel_size=8,
)

七、量化：显存减半，吞吐翻倍

量化对 LLM 的意义比传统模型更大——更小的模型权重意味着更少的显存带宽消耗，而 Decode 阶段正是带宽密集的。

FP8：H100 的原生加速

# TensorRT-LLM FP8 量化
import tensorrt_llm
from tensorrt_llm.quantization import QuantAlgo

# FP8 量化：精度接近 FP16，速度提升 1.5-2x
quantization = QuantAlgo.FP8
# 模型权重和激活值都用 FP8，H100 Transformer Engine 原生支持

FP8 几乎无精度损失（PPL 下降 <0.5%），是 H100 集群的首选量化方案。

AWQ/GPTQ：INT4 权重量化

from awq import AutoAWQForCausalLM
from transformers import AutoTokenizer

# AWQ INT4 量化：显存减少 75%，速度提升 2-3x
model = AutoAWQForCausalLM.from_pretrained("meta-llama/Llama-3-70b-instruct")
tokenizer = AutoTokenizer.from_pretrained("meta-llama/Llama-3-70b-instruct")

quant_config = {
    "zero_point": True,
    "q_group_size": 128,
    "w_bit": 4,           # 4-bit 权重
    "version": "GEMM"
}
model.quantize(tokenizer, quant_config=quant_config)
model.save_quantized("llama3-70b-awq-int4")

INT4 量化后 Llama-70B 权重约 35GB，但加上 activations、KV Cache 和框架开销，实际需要 45-50GB——A100-80GB 单卡勉强能跑，但 KV Cache 空间只剩 30-35GB，并发能力有限（约 100 个请求）。更现实的方案是 2 卡部署（每卡 ~25GB 权重），留出更多显存给 KV Cache，并发可达 200+。

KV Cache 量化

KV Cache 本身也可以量化，进一步节省显存：

# vLLM KV Cache INT8 量化
llm = LLM(
    model="meta-llama/Llama-3-70b-instruct",
    kv_cache_dtype="fp8",   # KV Cache 用 FP8 存储
    # 相比 FP16，KV Cache 显存减半，同等显存能服务 2 倍并发
)

八、并行策略：多卡多机扩展

张量并行（Tensor Parallelism）

把单层的权重矩阵切分到多张 GPU，每张 GPU 计算一部分，再 AllReduce 汇总：

Llama-70B，FP16，4 卡张量并行：
  每卡显存：140GB ÷ 4 = 35GB 模型权重
  A100-80GB：还剩 45GB 用于 KV Cache
  单节点最大并发：~100-150 请求

8 卡张量并行：
  每卡显存：140GB ÷ 8 = 17.5GB 模型权重
  A100-80GB：还剩 62.5GB 用于 KV Cache
  单节点最大并发：~200+ 请求（更多 KV Cache 空间）

张量并行的代价是每层都需要 AllReduce 通信，NVLink 带宽（600GB/s）足够；跨节点则要靠 InfiniBand（400Gb/s），延迟增加明显，通常不超过 2 个节点做 TP。

流水线并行（Pipeline Parallelism）

把模型按层切分到多个节点，适合超大模型（175B+）：

Llama-405B，4 节点流水线并行：
  节点1：Layer 1-25（前 25 层）
  节点2：Layer 26-50
  节点3：Layer 51-75
  节点4：Layer 76-101（后 25 层）

Micro-batch 流水填充：
  Batch 1: N1运算 → N2运算 → N3运算 → N4运算
  Batch 2: N1运算（Batch1在N2时）→ ...

流水线并行引入 bubble（流水线气泡），通常与张量并行组合使用（TP × PP = 总 GPU 数）。

九、Prefill-Decode 分离部署：工业级架构

这是 2024-2026 年大厂最重要的架构创新，字节（Mooncake）、百度、阿里都在实践。

为什么要分离

Prefill 阶段特性：
  - Compute-bound（算力密集）
  - 一个请求可以占满 GPU 算力几百毫秒
  - 适合大 batch，高 GPU 利用率

Decode 阶段特性：
  - Memory-bandwidth-bound（带宽密集）
  - 每步只处理一个 token，算力利用率极低
  - 需要保持大量 KV Cache 在显存中

问题：混合部署时，一个长 prompt 的 Prefill 会让所有并发的
      Decode 请求暂停等待，造成长尾延迟（TTFT 抖动严重）

分离架构设计

                    ┌─────────────────────────────────────┐
请求进来              │         路由层（Load Balancer）        │
   ↓                └──────────────┬──────────────────────┘
                                   │
              ┌────────────────────┴───────────────────┐
              ↓                                         ↓
  ┌─────────────────────┐               ┌──────────────────────┐
  │   Prefill 集群       │               │    Decode 集群        │
  │（算力优化，少量节点） │               │（显存优化，大量节点）  │
  │  高算力 GPU           │               │  大显存 GPU            │
  │  小 KV Cache         │   KV Cache    │  大 KV Cache          │
  │  大 batch prefill    │ ─────────► │  Continuous Batch     │
  └─────────────────────┘  传输给      └──────────────────────┘
                            Decode

KV Cache 迁移：Prefill 节点计算完 KV Cache 后，通过高速网络（RDMA/NVLink-C2C）传输给 Decode 节点，Decode 节点持续生成 token 直到完成。

最大的工程挑战：KV Cache 传输带宽

一个 Llama-70B 请求的 KV Cache 约 2.44GB（1000 token 序列）。如果每秒新增 140 万请求，理论需要 140w × 2.44GB = 3.4 PB/s 的传输带宽——这远超任何现有网络。实际上需要：

  • 尽量缩短 prompt 或启用 Prefix Caching（只传增量 KV Cache，不传缓存部分）
  • Prefill 和 Decode 节点尽量在同一机架或通过 NVLink 直连，而非跨节点 InfiniBand
  • KV Cache 量化到 FP8/INT8 再传输，减少 50-75% 传输量
  • 并非所有请求都需要 PD 分离，短 prompt 请求可以走混合部署

收益：

  • TTFT（Time To First Token）更稳定，不被 Decode 占用的 GPU 影响
  • Prefill 集群可以针对算力优化（更激进的 batch），Decode 集群针对显存优化
  • 独立扩容：请求量增加时只扩 Decode 集群；长 prompt 请求增加时扩 Prefill 集群

十、调度优化：请求级别的精细控制

优先级调度

# 不同业务优先级，避免低优先级请求阻塞高优先级
from vllm import LLM
from vllm.core.scheduler import SchedulingBudget

# 高优先级请求（付费用户、实时场景）优先分配资源
# 低优先级请求（离线任务、批处理）在 GPU 有余量时才执行

抢占式调度（Preemption）

当显存压力大时，vLLM 可以抢占低优先级请求（把它们的 KV Cache 换出到 CPU 内存），为高优先级请求腾出空间：

显存紧张时：
  1. 低优先级请求的 KV Cache 被 swap 到 CPU 内存（慢但不丢失）
  2. 高优先级请求使用腾出的显存继续推理
  3. 显存释放后，低优先级请求 swap 回来继续

代价：CPU 内存带宽 <<< GPU 显存带宽，swap 会增加延迟
适用：显存极度紧张时的保底手段，不建议频繁触发

Chunked Prefill：降低首 Token 延迟抖动

长 prompt 的 Prefill 会占用 GPU 很长时间，期间所有 Decode 请求无法推进。Chunked Prefill 把长 Prefill 切成小块，穿插在 Decode 步骤之间：

不分块：
  |────── Prefill(2000 tok, 500ms) ──────|Decode|Decode|...
  其他请求的 Decode 要等 500ms 才能推进 → 长尾延迟

Chunked Prefill（每块 256 token）：
  |Prefill chunk1|Decode×N|Prefill chunk2|Decode×N|...
  Decode 请求每 ~30ms 就能推进一步 → 延迟更平滑

  • 架构层：Prefill-Decode 分离需要自建调度层（参考 Mooncake 论文）

十二、成本优化：让每一张 GPU 都物尽其用

混合精度部署

不同层的精度敏感性不同：
  Embedding 层：对量化敏感，保持 FP16
  Attention 层：中等敏感，FP8 或 INT8
  FFN 层：相对不敏感，INT4 权重（AWQ）

混合精度策略：敏感层高精度，其他层低精度
  整体效果接近 FP16，显存接近 INT4

KV Cache 卸载到 CPU

# 多轮对话中，历史轮次的 KV Cache 卸载到 CPU 内存
# 当用户继续对话时，再从 CPU 加载回 GPU
llm = LLM(
    model="meta-llama/Llama-3-70b-instruct",
    cpu_offload_gb=40,  # 允许 40GB CPU 内存用于 KV Cache 卸载
)

弹性扩缩容

LLM 服务流量有明显的日/周规律（工作日白天高峰，凌晨低谷）。弹性扩缩容可以节省 40-60% 的成本：

  • 高峰期：全速部署，GPU 利用率 70-80%
  • 低谷期：缩容到最小集群，GPU 利用率提升到 90%+
  • 预测式扩容：基于历史流量预测，提前 5-10 分钟扩容，避免冷启动延迟

十三、关键点总结

  • LLM 推理是显存带宽密集型，不是算力密集型——优化的核心是 KV Cache 管理和显存带宽利用率
  • Continuous Batching 是基础设施，必须上——把 GPU 利用率从 20% 提升到 80%+，是所有其他优化的前提
  • PagedAttention 把显存利用率从 30% 提升到 90%——同等显存能服务 3 倍并发，是 vLLM 的核心价值
  • Prefix Caching 让 System Prompt 只算一次——生产环境节省 60-80% 的 prefill 计算量
  • 投机解码是 decode 阶段吞吐量的突破口——2-3x 吞吐提升，不牺牲延迟
  • 量化按场景选择：H100 用 FP8（几乎无损），A100 用 AWQ-INT4（大幅节省显存），精度敏感用混合精度
  • Prefill-Decode 分离是工业级架构的方向——两个阶段特性不同，分离部署各自优化，是百万 QPS 规模的必然选择
  • Chunked Prefill 解决延迟抖动——长 prompt 不再阻塞其他请求的 decode 推进
  • 成本意识贯穿始终——每 1% 的吞吐提升在这个规模下都价值数百万美元
