JVM GC 图解：从入门到真正理解垃圾回收

垃圾回收（Garbage Collection）是 JVM 最核心的运行时机制，也是 Java 性能调优的关键知识点。很多人用了多年 Java，却对 GC 的工作原理一知半解——知道有 Minor GC 和 Full GC，知道要避免频繁 Full GC，但说不清楚 G1 和 CMS 有什么本质区别，也不知道为什么 GC 会让应用暂停。

本文从最基础的内存结构开始，用大量图示一步步拆解 GC 的每个环节，力求让每个概念都有直觉上的理解。

一、JVM 堆内存结构

GC 管理的核心区域是堆（Heap）。JVM 启动时会申请一块连续内存作为堆，所有 new 出来的对象都在这里分配。

┌─────────────────────────────────────────────────────────────────┐
│                         JVM 堆内存                               │
│                                                                 │
│  ┌──────────────────────────────┐  ┌──────────────────────────┐ │
│  │           新生代（Young Gen）  │  │      老年代（Old Gen）     │ │
│  │                              │  │                          │ │
│  │  ┌────────┐ ┌─────┐ ┌─────┐ │  │  ┌────────────────────┐  │ │
│  │  │  Eden  │ │ S0  │ │ S1  │ │  │  │  长期存活的对象      │  │ │
│  │  │        │ │(from│ │(to) │ │  │  │  大对象             │  │ │
│  │  │  新对象 │ │)    │ │     │ │  │  │  静态变量引用的对象  │  │ │
│  │  │  在此  │ │     │ │     │ │  │  └────────────────────┘  │ │
│  │  │  分配  │ │     │ │     │ │  │                          │ │
│  │  └────────┘ └─────┘ └─────┘ │  │                          │ │
│  │   ~80%      ~10%    ~10%    │  │                          │ │
│  └──────────────────────────────┘  └──────────────────────────┘ │
│                                                                 │
│         Minor GC 管理新生代              Full GC 管理整个堆       │
└─────────────────────────────────────────────────────────────────┘

非堆区域（不由 GC 管理）：
  方法区（Metaspace）：类定义、常量池、静态变量
  程序计数器、虚拟机栈、本地方法栈（线程私有）

新生代分三个区：

  • Eden 区：新对象出生的地方，占新生代约 80%
  • Survivor 0（From）：上一次 Minor GC 后存活对象的暂居地
  • Survivor 1（To）：本次 Minor GC 时存活对象的目标地

这个设计来自一个重要的经验观察——分代假说。

二、分代假说：GC 设计的理论基础

JVM 内存分代设计基于两个经验规律：

弱分代假说：绝大多数对象都是"朝生夕死"的，极短命。
强分代假说：熬过多次 GC 的对象，未来也不太可能死。

用数据说话：实际 Java 程序中，一次 Minor GC 通常能回收 95%+ 的新生代对象。也就是说，大多数对象在 Eden 区被创建，在第一次 GC 时就死亡了，根本没有机会进入 Survivor 区。

对象存活率随年龄的变化（示意）：

存活率
100% │
     │  ███
 50% │     ████
     │         ████
 10% │              ████████
  5% │                      █████████████████（趋于稳定）
  0% └─────────────────────────────────────────────────→ GC 轮次
      1次  2次  3次  4次  5次  6次  7次  8次  ...

绝大多数对象在第 1 次 GC 就被回收
少数"长命"对象在多次 GC 后趋于稳定存活

这个规律决定了：

  • 新生代可以用复制算法——只有少数对象需要被复制，效率极高
  • 老年代对象密度高，不适合复制，用标记-整理或标记-清除
  • 新生代 GC（Minor GC）可以频繁运行，开销小；老年代 GC（Full GC）代价大，要尽量避免

三、Minor GC：新生代的清理过程

当 Eden 区满了，就触发 Minor GC。整个过程分四步：

第一步：Eden 区满，触发 GC

Minor GC 触发前：

┌──────────────────────────────────────────────────────────┐
│ Eden（已满）                       │ S0（有存活对象）│ S1 │
│ ████████████████████████████████  │ ████            │    │
│ A  B  C  D  E  F  G  H  I  J  K  │ X  Y            │    │
│ ↑活  ↑死 ↑活 ↑死 ↑死 ↑活 ↑死 ↑活 ↑死 ↑死 ↑死│ ↑活↑活         │    │
└──────────────────────────────────────────────────────────┘

  Eden 区对象：A C F H 存活，其余死亡
  S0 对象：X Y 存活（已经经历过一次 GC，年龄=1）

第二步：标记存活对象（可达性分析）

GC Roots（根对象）：
  · 当前线程栈帧中的局部变量
  · 方法区中的静态变量
  · JNI 引用

从 GC Roots 出发，遍历引用链，能到达的对象 = 存活：

  GC Root ──→ A（存活）──→ C（存活）
  GC Root ──→ F（存活）
  GC Root ──→ H（存活）
  GC Root ──→ X（存活）──→ Y（存活）

  B D E G I J K：不可达 = 垃圾 ← 等待回收

第三步：复制存活对象到 S1（To 区），年龄 +1

复制后状态：

┌──────────────────────────────────────────────────────────┐
│ Eden（清空）                       │ S0（清空）│  S1       │
│                                   │           │  A  C     │
│                                   │           │  F  H     │
│                                   │           │  X  Y     │
│                                   │           │ 年龄：1 1 1 1 2 2 │
└──────────────────────────────────────────────────────────┘

  Eden 中的存活对象（A C F H）复制到 S1，年龄从 0 变为 1
  S0 中的存活对象（X Y）复制到 S1，年龄从 1 变为 2
  Eden 和 S0 全部清空（直接丢弃所有对象，无需逐个释放）

第四步：S0/S1 角色互换

互换后：S1 变为新的 S0（From），原 S0 变为新的 S1（To）

下一次 Minor GC 时，新的存活对象将被复制到新的 To 区（原 S0）

新对象继续在 Eden 分配 ↓

┌──────────────────────────────────────────────────────────┐
│ Eden（接收新对象）                  │ S0(From)  │  S1(To) │
│ 新对象...                          │ A C F H   │  空      │
│                                   │ X Y       │          │
│                                   │ 年龄：1 1 1 1 2 2     │          │
└──────────────────────────────────────────────────────────┘

何时晋升老年代？

两种情况会让对象从新生代晋升到老年代：

1. 年龄阈值（默认 15）：
   对象每熬过一次 Minor GC，年龄 +1
   年龄达到 MaxTenuringThreshold（默认 15）时，晋升老年代

   年龄:  1    2    3  ...  15   → 进入老年代
          ↑    ↑    ↑        ↑
        GC1  GC2  GC3      GC15

2. 大对象直接进老年代：
   超过 -XX:PretenureSizeThreshold 的对象直接分配在老年代
   避免大对象在 Eden/Survivor 区来回复制的巨大开销

四、Full GC：最昂贵的操作

Full GC 会回收整个堆（新生代 + 老年代），期间会触发 Stop-The-World（STW）——暂停所有用户线程，直到 GC 完成。

Stop-The-World 示意：

时间轴 →
─────────────────────────────────────────────────────────────
用户线程：████████████████  ←暂停→  ████████████████████████
GC 线程：                ████████████████
─────────────────────────────────────────────────────────────
                         ↑ STW 开始    ↑ STW 结束
                     所有请求在这段时间内无响应！

Full GC 的 STW 时间：几百毫秒到几秒不等
→ 这就是为什么 Full GC 对线上服务是灾难性的

触发 Full GC 的常见原因：

1. 老年代空间不足
   ┌────────────────────────────────────┐
   │  老年代（95% 已满）                  │  ← 新对象晋升时放不下
   │  ████████████████████████████████  │     → 触发 Full GC
   └────────────────────────────────────┘

2. Minor GC 晋升失败（Promotion Failure）
   老年代剩余空间 < 新生代存活对象总大小
   JVM 无法保证晋升成功 → 触发 Full GC

3. 显式调用 System.gc()（强烈不建议）

4. Metaspace 空间不足（类加载过多）

5. CMS GC 的并发失败（Concurrent Mode Failure）

五、可达性分析：判断对象是否存活

GC 如何知道哪些对象可以回收？答案是可达性分析（Reachability Analysis）。

对象引用图示例：

GC Roots
    ├──→ 对象A ──→ 对象C ──→ 对象E
    │         └──→ 对象D（无外部引用指向它，但被 A 引用）
    └──→ 对象B

    对象F ──→ 对象G
    （F 和 G 互相引用，但没有 GC Root 能到达它们）

可达对象（存活）：A B C D E
不可达对象（垃圾）：F G ← 即使 F→G→F 形成循环引用，也会被回收

这是可达性分析相比"引用计数"的核心优势：
  引用计数无法处理循环引用（F.count=1, G.count=1，永远不为0）
  可达性分析从根出发，循环引用的孤岛自然不可达

GC Roots 包含哪些？

┌─────────────────────────────────────────────────────────────┐
│                      GC Roots 来源                           │
├─────────────────────────────────────────────────────────────┤
│  1. 虚拟机栈中的引用                                          │
│     void method() {                                         │
│         Object obj = new Object();  ← obj 是 GC Root        │
│     }  // 方法返回后 obj 不再是 GC Root，对象可被回收         │
│                                                             │
│  2. 方法区中的静态变量                                        │
│     static Object shared = new Object();  ← GC Root         │
│     只要类还被加载，shared 就一直是 GC Root                   │
│                                                             │
│  3. 方法区中的常量                                            │
│     static final String NAME = "hello";  ← GC Root          │
│                                                             │
│  4. JNI 引用（本地方法持有的 Java 对象引用）                   │
└─────────────────────────────────────────────────────────────┘

六、四种引用类型：影响 GC 行为的关键

强度递减 →

强引用（Strong Reference）      弱引用（Weak Reference）
Object obj = new Object();     WeakReference<Object> wr = ...
↓ 只要存在，永远不会被 GC 回收    ↓ 下次 GC 时必然被回收，不管内存是否充足

软引用（Soft Reference）         虚引用（Phantom Reference）
SoftReference<Object> sr = ... PhantomReference<Object> pr = ...
↓ 内存充足时保留，内存不足时回收   ↓ 几乎等于没有引用，专门用于追踪 GC 事件
  （适合实现内存敏感的缓存）
// 软引用：实现 LRU 缓存的经典方案
Map<String, SoftReference<BigImage>> imageCache = new HashMap<>();

// 存入缓存
imageCache.put("logo", new SoftReference<>(loadImage("logo.png")));

// 取出缓存
SoftReference<BigImage> ref = imageCache.get("logo");
BigImage img = ref != null ? ref.get() : null;  // 可能为 null（已被 GC 回收）
if (img == null) {
    img = loadImage("logo.png");  // 重新加载
    imageCache.put("logo", new SoftReference<>(img));
}

// 优点：内存充足时命中缓存（快），内存紧张时 GC 自动清理（不 OOM）

七、三种基础 GC 算法

标记-清除（Mark-Sweep）

GC 前：
┌────────────────────────────────────────────────────────┐
│ [A活][B死][C活][D死][E死][F活][G死][H活][I死][J活]      │
└────────────────────────────────────────────────────────┘

标记阶段：标记所有存活对象
┌────────────────────────────────────────────────────────┐
│ [A★] [B  ] [C★] [D  ] [E  ] [F★] [G  ] [H★] [I  ] [J★] │
│  ↑存活        ↑存活             ↑存活        ↑存活        ↑存活│
└────────────────────────────────────────────────────────┘

清除阶段：释放未标记的对象
┌────────────────────────────────────────────────────────┐
│ [A  ] [   ] [C  ] [   ] [   ] [F  ] [   ] [H  ] [   ] [J  ] │
│  ↑存活  ↑空洞  ↑存活  ↑空洞  ↑空洞  ↑存活  ↑空洞  ↑存活  ↑空洞  ↑存活│
└────────────────────────────────────────────────────────┘

问题：内存碎片！大量不连续的小空洞，分配大对象时找不到足够大的连续空间

标记-复制（Mark-Copy）

内存分为两半：From 和 To

GC 前（From 半区有对象，To 为空）：
From: [A活][B死][C活][D死][E活][F死][G活]
To:   [                              ]

GC 后（存活对象紧凑复制到 To，From 整体清空）：
From: [                              ]
To:   [A   ][C   ][E   ][G   ]
       ↑紧凑排列，无碎片

优点：无碎片，分配速度极快（只需移动指针）
缺点：内存利用率只有 50%

这就是为什么新生代 Survivor 区只有 10%：
  Eden(80%) + S0(10%) → 复制到 S1(10%)
  实际利用率 90%，只浪费 10%（而不是 50%）
  前提是新生代存活率低（通常 <5%，10% 的 S 区足够）

标记-整理（Mark-Compact）

GC 前：
[A活][B死][C活][D死][E死][F活][G死][H活]

标记后，将存活对象向一端移动（整理）：
[A活][C活][F活][H活][         空闲         ]
  ↑存活对象紧凑排列       ↑连续大块空闲空间

优点：无碎片，内存利用率 100%
缺点：需要移动对象，移动时要更新所有引用指针，开销大

适合老年代：老年代对象存活率高，复制算法代价太大；
           标记-整理能解决碎片问题，偶尔执行一次整理可以接受

八、五大主流垃圾收集器

Serial GC：单线程，最简单

特点：GC 时只用一个线程，STW 期间用户线程全部暂停

时间轴：
用户线程: ████████████ ←──── STW ────→ ████████████████
GC 线程:              ████████████████

适用：客户端应用，单核 CPU，几十到几百 MB 堆
启用：-XX:+UseSerialGC

Parallel GC：多线程 Serial，吞吐量优先

特点：GC 用多个线程并行工作，缩短 STW 时间，但仍然 STW

时间轴：
用户线程: ████████████ ←── STW（更短）──→ ████████████████
GC 线程1:              ███████████
GC 线程2:              ███████████
GC 线程3:              ███████████

适用：后台计算任务，不在意单次暂停，在意总吞吐量
JDK 8 默认收集器
启用：-XX:+UseParallelGC

CMS GC：并发收集，低停顿（已废弃）

目标：让 GC 和用户线程尽量并发执行，减少 STW 时间

时间轴：
用户线程: ████│ STW │████████████████████████████│STW│████████
GC 线程:       ████  ████████████████████████████  ████
                初始  ↑──── 并发标记（与用户线程同时跑）────↑  重新
                标记                                        标记

CMS 四个阶段：
1. 初始标记（STW，很短）：只标记 GC Roots 直接引用的对象
2. 并发标记（与用户线程并发）：从 GC Roots 出发遍历整个引用图
3. 重新标记（STW，较短）：修正并发标记期间用户线程修改的引用
4. 并发清除（与用户线程并发）：清除不可达对象

问题：
1. 并发清除时产生「浮动垃圾」（刚被标记为存活，并发期间变成垃圾）
2. 使用标记-清除，会产生内存碎片
3. 如果老年代在并发阶段被填满，会触发 Serial Old 兜底（极慢！）

JDK 14 中被废弃，建议迁移到 G1

G1 GC：分区设计，可预测停顿（JDK 9+ 默认）

G1 最大的创新：把堆划分为大量小的「Region」，每个 Region 约 1-32MB

┌────────────────────────────────────────────────────────────────┐
│                    G1 堆布局（Region 视图）                      │
│                                                                │
│  ┌──┐ ┌──┐ ┌──┐ ┌──┐ ┌──┐ ┌──┐ ┌──┐ ┌──┐                    │
│  │E │ │E │ │S │ │O │ │E │ │O │ │H │ │O │                    │
│  └──┘ └──┘ └──┘ └──┘ └──┘ └──┘ └──┘ └──┘                    │
│  ┌──┐ ┌──┐ ┌──┐ ┌──┐ ┌──┐ ┌──┐ ┌──┐ ┌──┐                    │
│  │O │ │E │ │H │ │O │ │S │ │E │ │O │ │  │  （空闲）           │
│  └──┘ └──┘ └──┘ └──┘ └──┘ └──┘ └──┘ └──┘                    │
│                                                                │
│  E = Eden Region    S = Survivor Region                        │
│  O = Old Region     H = Humongous Region（大对象，跨多个 Region）│
└────────────────────────────────────────────────────────────────┘

G1 的核心优势：优先回收「垃圾最多」的 Region

每个 Region 都记录了「回收收益」（能回收多少空间）和「回收代价」（需要多少时间）
G1 每次选择收益/代价最高的 Region 集合进行回收（Garbage First = 垃圾优先）

停顿目标：可以设置期望的最大停顿时间
-XX:MaxGCPauseMillis=200  // 期望每次 GC 暂停不超过 200ms
G1 会根据这个目标动态调整每次回收的 Region 数量
G1 Mixed GC 流程：

阶段1：初始标记（STW，随 Minor GC 一起执行，几乎无额外停顿）
  标记 GC Roots 直接引用的对象

阶段2：并发标记（与用户线程并发，可能持续几百毫秒）
  从 GC Roots 出发，遍历整个堆，记录每个 Region 的存活数据

阶段3：最终标记（STW，很短）
  处理 SATB（Snapshot-At-The-Beginning）缓冲区，修正并发阶段的变化

阶段4：筛选回收（STW，可控时长）
  根据各 Region 的回收价值，在停顿时间限制内，选择最有价值的 Region 回收
  使用复制算法，将存活对象复制到空 Region，原 Region 整体释放（无碎片！）

ZGC：亚毫秒级停顿（JDK 15+ 生产可用）

ZGC 的目标：无论堆多大（TB 级），停顿时间始终 < 10ms（通常 1-2ms）

实现原理：几乎所有工作都与用户线程并发执行

时间轴：
用户线程: ████████████████████████████████████████████████
GC 线程:   ████████████████████████████████████████████████
STW:             │1ms│                   │1ms│

关键技术：
1. 染色指针（Colored Pointer）：在对象指针的高位存储 GC 状态信息
   64位指针中，高4位用于标记（Marked0/Marked1/Remapped/Finalizable）
   好处：不需要额外的标记位图，GC 状态和对象绑定

2. 读屏障（Load Barrier）：每次读取对象引用时，检查并修正指针
   用户线程每次访问对象时，顺带完成"重定位"工作
   把"移动对象后更新引用"的工作分散到每次对象访问中

3. 并发整理：对象可以在用户线程运行时被移动（配合读屏障保证正确性）

适用：对延迟极度敏感的服务（金融交易、实时推荐、游戏服务器）
启用：-XX:+UseZGC（JDK 11+，生产推荐 JDK 15+）

五大收集器对比总结

收集器新生代算法老年代算法停顿特点适用场景
Serial复制标记整理STW，单线程客户端/单核/小堆
Parallel复制标记整理STW，多线程后台批处理，吞吐优先
CMS（配合 ParNew）标记清除短暂 STW + 并发已废弃，迁移到 G1
G1复制复制可设定目标停顿大堆（4GB+），通用服务
ZGC并发，全堆统一<10ms，与堆大小无关超大堆，延迟敏感服务

关键 JVM 参数

# 堆大小
-Xms4g -Xmx4g          # 初始和最大堆大小，建议设成相同值（避免动态扩容开销）
-Xmn1g                 # 新生代大小（一般为堆的 1/4 到 1/3）

# 选择收集器
-XX:+UseG1GC           # 使用 G1（JDK 9+ 默认）
-XX:+UseZGC            # 使用 ZGC（延迟敏感场景）

# G1 调优
-XX:MaxGCPauseMillis=200    # 期望停顿不超过 200ms
-XX:G1HeapRegionSize=16m    # Region 大小（1-32m，2 的幂次）

# GC 日志（必须开，出问题时救命）
-Xlog:gc*:file=/logs/gc.log:time,uptime,level,tags:filecount=5,filesize=20m

常见问题诊断

问题 1：频繁 Full GC

诊断步骤：
  1. jstat -gcutil <pid> 1000   # 每秒看一次 GC 情况
  2. 观察 OU（Old 使用率）是否持续增长
  3. 如果 OU 线性增长 → 内存泄漏（对象无法被回收）
  4. 如果 OU 周期性满 → 老年代容量不足，考虑扩大 -Xmx 或 -Xmn

问题 2：GC 停顿过长

诊断步骤：
  1. 分析 GC 日志，找出停顿 > SLA 的 GC 事件
  2. 查看是 Minor GC 还是 Full GC
  3. Minor GC 慢 → 新生代太大，或存活对象太多（阈值设太高）
  4. Full GC 慢 → 老年代碎片（CMS），或堆太大（G1 Region 太多）

问题 3：OOM（OutOfMemoryError）

常见原因：
  java.lang.OutOfMemoryError: Java heap space
    → 堆内存不足，对象太多或内存泄漏

  java.lang.OutOfMemoryError: Metaspace
    → 动态生成类太多（如 AOP、反射、动态代理），
      增大 -XX:MaxMetaspaceSize

  java.lang.OutOfMemoryError: GC overhead limit exceeded
    → GC 时间占总时间比例超过 98%，几乎不做实际工作
      通常是内存严重不足的信号

十、关键点总结

  • 堆分新生代和老年代，基于分代假说：大多数对象短命，少数长寿；不同代用不同算法
  • Minor GC 用复制算法：Eden → Survivor，年龄到阈值晋升老年代；快速、频繁，影响小
  • Full GC 触发 Stop-The-World：整个堆暂停，代价极大，要尽量避免；老年代满、晋升失败是主要触发原因
  • 可达性分析从 GC Roots 出发判断存活，能正确处理循环引用（引用计数做不到）
  • 三种基础算法：标记-清除（有碎片）、标记-复制（无碎片但费内存）、标记-整理（无碎片，但移动对象开销大）
  • G1 是当前通用默认选择：Region 化设计，可设定停顿目标，无碎片，适合 4GB+ 的堆
  • ZGC 是延迟敏感场景的终极方案：染色指针 + 读屏障实现并发整理，停顿 <10ms 且与堆大小无关
  • GC 日志是调优的基础：生产环境必须开启 GC 日志，出问题时是最重要的诊断依据
